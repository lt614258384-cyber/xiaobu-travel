# 小布的旅行：跨 Agent 项目日志设计

## 目标

建立一份可持续维护的项目单一事实源，使任何新 Agent 在不了解历史对话的情况下，都能快速理解项目目标、当前状态、风险、决策和下一步工作，并在结束项目相关对话前留下可验证的交接记录。

## 文件结构

### `docs/PROJECT_LOG.md`

项目主日志，包含：

1. 日志维护协议与保密规则。
2. 项目目标、用户价值和当前范围。
3. 仓库、分支、技术栈、启动与测试方式。
4. 当前架构与关键数据流。
5. 已完成事项及其验证状态。
6. 当前问题、安全隐患和部署阻塞项。
7. 按阶段整理的待办、优先级和依赖关系。
8. 已确认的设计决策及理由。
9. 当前最优先的下一步和交接提示。
10. 按日期倒序追加的项目对话与开发记录。

### `AGENTS.md`

仓库级 Agent 指令，要求所有后续 Agent：

- 开始工作前阅读 `docs/PROJECT_LOG.md` 和与任务相关的规格文档。
- 结束每次项目相关对话前更新项目日志；即使没有代码改动，也记录新发现、决策或“无状态变化”。
- 只把经过验证的工作标记为完成，计划中或未验证的工作保持待办状态。
- 不在日志、提交、终端输出或测试夹具中记录密码、API Key、Session Token、Cookie、真实邮箱等秘密或个人数据。
- 保留其他 Agent 和用户的未提交改动，不重写历史记录。

## 更新规则

- 使用 Asia/Hong_Kong 日期和时间。
- 当前状态章节保持精炼并持续更新；历史记录采用追加方式，不删除重要决策。
- 每条会话记录至少包含：日期、执行者/Agent、用户目标、完成的检查或改动、验证证据、遗留问题和下一步。
- 若本次仅调查或讨论，明确写“无代码改动”，并记录得到的结论。
- 任何状态变化必须同时更新对应待办项，避免“历史记录说完成、当前待办仍未完成”的矛盾。

## 初始内容来源

首次建立日志时，从以下已验证来源汇总：

- `docs/CONTEXT.md` 的项目背景、核心功能和已知问题。
- 当前 Git 分支、最近提交和工作区状态。
- 已提交的可靠性清理设计与实施计划。
- 当前代码中的单用户架构和多用户改造目标。
- 2026-06-22 安全审计中确认的鉴权、CSRF、上传、API Key、依赖和公开媒体风险。

## 保密与准确性

- 日志只记录秘密的存储位置和处理要求，不记录秘密值。
- 不读取或摘录真实数据库、上传照片、视觉特征缓存和 `.env` 内容来填充日志。
- “已完成”必须有提交、测试输出或文件证据；未实现的规格和计划不得被误写为完成。
- 无法验证的结论标记为“待确认”，并写明验证方式。

## 验收标准

- 新 Agent 仅阅读 `AGENTS.md` 和 `docs/PROJECT_LOG.md`，即可知道项目目标、当前风险、下一步和禁止事项。
- 日志能区分已完成、进行中、待办、阻塞和待确认。
- 当前已知安全隐患与多用户改造阶段均有明确记录。
- 根目录指令清楚要求每次项目对话结束前更新日志。
- 文件中不包含任何真实秘密或个人数据。
